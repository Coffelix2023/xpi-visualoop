# 评审专家修改openspec 计划的意见:

 TL;DR

 方向对,打包方式错。砍掉 Python 后端是正确且必要的(Pi 包机制只跑 npm install,这是硬约束,已核实)。但
 这个 change 把三件互相独立的事绑成一次提交,并且建立在一个红色基线上。建议拆成两个 change,并先补两
 个计划里没写的洞。

 我实际核对过的现状:spawn(config.harnessPath) + 内嵌 Python + PIL(Python Imaging Library,Python 图
 像库)确实是三层套壳去访问一个 WebSocket 上的 JSON-RPC(远程过程调用)协议;pnpm test 当前 5 个用例失
 败,全部来自 context.ts:701 的端点锁 EEXIST。

 一、计划做对的部分

 - 依赖倒置的诊断准确。用 Node 进程直连 CDP,删掉的代码远多于新增的代码,这是最好的一类变更。
 - Node 24 内置 WebSocket 承载 CDP 是合理判断。CDP 只需要文本帧,回环连接不太需要 ping/pong 保活,ws
   作为回退点已记录。
 - 决策四(可比性单点判据)找到了真问题。我确认 evidence.ts:compareCaptureConditions 把 degraded 记为
   原因,而 context.ts 另有硬拒逻辑,同一次复核结论取决于走哪条路径。
 - 决策七 fail-closed 拒绝旧字段,与 config.ts 现有的未知字段态度一致,没问题。
 - 21MiB 的数字算得对:Python 侧 MAX_IMAGE_BYTES = 4MiB × 4 张图,base64 膨胀后就是这个量级。

 二、必须改的五个问题(按严重度排)

 ### 问题 1:一个 change 装了三件独立的事

 里面其实是:

 ┌─────────────────────────────────────┬──────────────────┬──────────────────┐
 │ 子变更                              │ 风险             │ 依赖传输层改造吗 │
 ├─────────────────────────────────────┼──────────────────┼──────────────────┤
 │ A. 传输层换成进程内 CDP             │ 高,约 900 行重写 │ ——               │
 ├─────────────────────────────────────┼──────────────────┼──────────────────┤
 │ B. 可比性判据 + stateLabel 显式契约 │ 低,纯逻辑        │ 不依赖           │
 ├─────────────────────────────────────┼──────────────────┼──────────────────┤
 │ C. 复核输出上界                     │ 低,纯逻辑        │ 不依赖           │
 └─────────────────────────────────────┴──────────────────┴──────────────────┘

 B 和 C 落在 evidence.ts 与 context.ts,和后端是谁完全无关。绑在一起的后果:你自己在 Why 里把「假验证
 」列为最严重的正确性缺陷,却让它被一个高风险重写挡在门后;而 Migration Plan 第 4 条的回滚是「还原
 harness.ts 与 config.ts」,一旦回滚,B/C 的修复也一起没了。

 建议:拆成 fix-verification-comparability(B+C,无 BREAKING,可立即发布)和
 replace-harness-with-native-cdp(A)。前者先落地先受益,后者慢慢验。

 ### 问题 2:红色基线被当成脚注,而它本身是个用户可见缺陷

 任务 1.3 只是「记录基线并确认失败是否与端点锁竞争有关」。我跑过了,就是端点锁:context.ts 用文件锁做
 互斥,EEXIST 时直接抛「endpoint is already owned by another xpi-visualoop process」。

 这不只是测试卫生问题。它意味着锁没有可靠的释放路径:进程崩溃或被 kill 之后残留锁文件,扩展就永久不可
 用,直到人类手动删文件。这比 proposal 里任何一条都更容易被真实用户撞到,而计划的 Non-Goals 明确保留
 这套互斥语义、§4.9 只讲连接释放,没碰锁。

 建议:把「锁记录持有者 PID(进程标识)与时间戳,发现持有者已不存在则抢占」提进 1.x 作为前置任务。这大
 概十几行。另外,在红色基线上开始重写等于放弃了区分新旧故障的能力,必须先绿再动。

 ### 问题 3:决策二(每次操作一个短连)和 §4.6 的诊断需求互相矛盾

 这是技术上最尖锐的一处。控制台错误和网络失败在 CDP 里是推送事件,不 attach、不 enable 就没有观察窗
 口。短连模式下,两次操作之间发生的一切都不存在。Log.enable 会重放部分已缓冲条目
 ,Runtime.consoleAPICalled 和 Network 域基本不重放(这条请在实测中确认,不要照我说的写)。

 结论:短连下 §4.6 的 unknown 不是异常分支,而是常态。于是你花 §4.5 和 §4.6 两个任务忠实复刻的诊断能
 力,产出接近于零。旧 Python 实现是每次操作一个进程,同样有这个洞;计划却要求「与既有实现等价」,等于把
 一个坏功能忠实地重新实现一遍。

 建议:连接生命周期改为等于检查上下文生命周期(prepare 建立,close 释放),而不是每次操作。理由:

 - 这不违反「不引入 daemon(常驻守护进程)」的 Non-Goal。prepare/close 已经定义了一个所有权窗口,连接
   跟它对齐是最自然的,不是跨会话共享。
 - 诊断因此获得真实观察窗口,§4.6 才有意义。
 - 决策二的代价(握手开销)和 Open Questions 里那条「短连成本是否可接受」同时消失,不需要实测。
 - 状态机没有变复杂:窗口的开合点本来就是那两个动作。

 如果不改连接模型,那就诚实地删掉网络诊断,别重写它。两条路都行,忠实复刻是最差的一条。

 ### 问题 4:任务 4.7 和保留的 spec 条文冲突

 visual-evidence 里这句没改:「局部图 SHALL 从该次视口图派生」。但任务 4.7 是「用
 Page.captureScreenshot 的区域参数实现视口截图与局部截图」,即两次独立截图。两次截图就是对一个可能已
 变化的页面采了两次样,局部图不再从同一批像素派生。对一个卖点是「可信前后对比」的产品,这是实质削弱。

 根因是 Node 没有内置图像解码器,不引依赖就无法本地裁 PNG,所以只能靠 clip 再拍一次。那就正面处理,别
 让 spec 和 task 各说一套。三个选项:

 1. 改 spec 条文,承认局部图是同一状态下的第二次采样,并在两次之间做稳定性校验(你已有前后稳定性检测机
    制)。
 2. 只发一次 clip 截图,视口图按需再取。
 3. 引入最小图像库,与「零依赖增量」目标冲突,不推荐。

 我倾向 1,但必须显式改 spec,不能留着旧条文当既成事实。

 顺带:决策三说 clip 的坐标是 DIP(device independent pixel,设备无关像素)、与 visibleBounds 的 CSS 像
 素同系。在 Emulation.setDeviceMetricsOverride 叠加页面缩放时这两者会分叉,你已把它标为未验证项并备
 了视口 1000×1000 的兜底,这个处理是诚实的,保留。

 ### 问题 5:预算是个不可验证的目标

 spec 里反复出现「为证据输出设定的预算」,但全文没有数字。文本预算有(16KiB,与采集一致),图像总量没有
 。任务 3.3 要「建立预算断言」,断言一个未定义的量。

 而且 evidence.ts 的 EvidenceLimits { maxBytes, maxCaptures } 是临时文件磁盘预算,和「注入模型的上下
 文预算」是两回事。同名不同物,实现时几乎一定会串。

 建议:在 spec 里写死两个具名数字,并把两个预算改成不同的名字,比如 evidenceDiskBudget 与
 modelPayloadBudget。没有数字的预算等于没有预算。

 三、两个较轻但值得动的点

 目标与约束被轻微混淆。 你不能有的是 Python 与 PyPI(Python 包索引),因为 npm install 分发不了它;ws
 恰好是能分发的。所以「零新增运行时依赖」是加分项,「不要 Python」才是硬要求。内置 WebSocket 仍然是
 对的选择,但回退到 ws 应该有判据(出现分片、背压或断连控制不足即回退),而不是凭感觉。

 Chrome 授权弹窗的验证时机太晚。 风险一节提到 Chrome 144+ 的连接级授权弹窗,而你真机是 Chrome 152。
 它是唯一能一票否决整个方案的未知项,却排在 4.8 和 6.1。请在 1.x 加一个五分钟的连通性 spike:内置
 WebSocket 直连一次 /json/version 与一个 target,看有没有弹窗、弹几次。顺便说,如果弹窗是每连接一次,
 短连模式就是每次操作弹一次,可用性直接归零,这是问题 3 改连接模型的第二个理由。

 交付性目标只完成了一半。 删掉 Python 之后,首次使用仍然要求用户自己带 --remote-debugging-port 和独
 立 --user-data-dir 启动 Chrome、再手写一个 JSON 配置。这个门槛比 Python 更高。Non-Goal 里不做自动
 发现和自动启动,作为范围纪律我同意,但既然 6.3 本来就要重写 README,顺手放一条可直接复制粘贴的启动命
 令,成本几乎为零。
